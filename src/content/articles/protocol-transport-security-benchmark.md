## 为什么协议选型在 2026 年变成了一个工程问题

早期代理协议的选择逻辑很简单：能连上、不被封就行。如今链路环境已经分化得相当明显——跨境专线、家宽直连、移动蜂窝网络、校园网与酒店网络，各自的丢包率、RTT 抖动和 UDP 策略完全不同。同一条节点，在丢包 1% 的链路上跑得飞快，换到丢包 12% 的晚高峰蜂窝网络可能连网页都打不开。

VLESS Reality、TUIC、Hysteria2 这三个名字经常被并列讨论，但它们解决的问题并不在同一层面。Reality 解决的是"如何让代理流量在主动探测下不被识别"，属于伪装层；TUIC 和 Hysteria2 解决的是"在不可靠链路上如何把吞吐和延迟做上去"，属于传输层。把三者放在同一张表里比"谁更快"，本身就需要先厘清比较维度。

本文从握手特征、拥塞控制模型、弱网实测机制三个角度拆解，并给出可落地的调优参数与失败回退方案。

## 三种协议的底层架构与伪装机制剖析

### VLESS Reality：不持有证书的 TLS 借用

传统 TLS 伪装方案（如 Trojan、VLESS+WS+TLS）要求服务端持有真实域名与证书，问题在于：一旦证书链被关联到代理服务，或者服务端在探测请求下返回了与伪装站点不一致的响应，指纹就会暴露。

Reality 的思路是彻底放弃自有证书。服务端在握手时扮演一个"中间人"，把客户端的 ClientHello 转发给一个真实的目标站点（如某大型 CDN 的落地服务器），将对方返回的 ServerHello 与证书链原样回传给客户端。客户端并不校验证书链的 CA 签名，而是校验服务端是否持有与预共享公钥对应的私钥——通过 TLS 1.3 的密钥派生过程完成隐式认证。

这套机制带来的直接效果是：主动探测器看到的握手过程与访问真实目标站点几乎一致，包括证书、TLS 版本、扩展字段顺序。未持有公钥的探测者无法完成认证，会被转发到目标站点的真实页面，得到正常的 HTTPS 响应。

代价是部署时对目标站点的选择有要求：TLS 版本需为 1.3，目标站点需支持 X25519 密钥交换，且其握手特征应稳定。目标站点若发生证书轮换或协议降级，需要同步调整。

### TUIC：标准 QUIC 上的轻量封装

TUIC 建立在标准 QUIC 之上，利用 QUIC 的 0-RTT 握手、多路复用与连接迁移能力。它的协议设计相对克制：认证与数据帧封装在 QUIC 流内，拥塞控制通常沿用 QUIC 实现自带的算法（Cubic 或 BBR 变体），不做过度的私有化改造。

这种"克制"带来的好处是链路公平性较好，与同链路上的其他 QUIC 流量（HTTP/3 等）能够共存；代价是在高丢包环境下，标准拥塞控制会按规则收缩窗口，吞吐下降明显。

### Hysteria2：为劣质链路设计的 QUIC 变体

Hysteria2 同样基于 QUIC，但做了两处关键改造。其一是 Brutal 拥塞控制：发送端不依据丢包信号降低速率，而是按照用户配置的上下行带宽固定节奏发包，仅在检测到持续严重拥塞时有限退让。其二是更激进的前向纠错与重传策略，在丢包发生时优先保证有效吞吐。

这两处改造让它在中高丢包链路上表现突出，但也意味着它不具备链路公平性——同一网络下的其他流量会被挤压。这一点在共享网络环境中必须纳入考量。

## 参数与特性对照表

下表汇总三种协议在关键维度上的差异，便于横向定位。表中"典型适用场景"基于常见网络环境归纳，实际表现受运营商策略与线路质量影响。

| 维度 | VLESS Reality | TUIC | Hysteria2 |
| --- | --- | --- | --- |
| 底层传输 | TCP + TLS 1.3（可配 XTLS Vision） | QUIC（UDP） | QUIC 变体（UDP） |
| 伪装方式 | 借用真实站点证书链，无自有证书 | TLS 证书或预共享密钥 | TLS 证书或自签 + 混淆密码 |
| 抗主动探测 | 强，握手特征与真实站点一致 | 中等，依赖证书与 SNI 配置 | 中等偏弱，UDP 特征较明显 |
| 拥塞控制 | 由 TCP 栈决定（BBR/Cubic 可选） | Cubic / BBR 类标准算法 | Brutal 固定速率模型 |
| 弱网吞吐（丢包 >8%） | 受 TCP 重传拖累，下降明显 | 中等，窗口收缩后恢复较慢 | 优势明显，维持较高吞吐 |
| 链路公平性 | 好 | 好 | 较弱，具抢占性 |

| 部署复杂度 | 中（需选好回落目标） | 中（证书与 UDP 端口） | 中（带宽参数需调） |
| 主要风险 | 回落目标失配导致指纹异常 | UDP 被 QoS 限速 | 带宽参数过高引发拥塞与限速 |

## 弱网抗丢包：机制差异如何转化为体验差异

理解三者差异的关键在于看清"丢包发生时，发送端做什么"。

TCP 系（Reality）在检测到丢包后触发重传与拥塞窗口收缩，RTT 越高，重传等待越久。在 RTT 200ms、丢包 10% 的链路上，一次丢包可能带来数百毫秒的停顿，表现为网页加载卡顿、视频缓冲。

TUIC 依托 QUIC 的流级多路复用，单个流的丢包不会阻塞其他流，这在多标签页并发场景下体验改善明显。但其拥塞控制仍遵循标准逻辑，整体吞吐在高丢包下依然会下降。

Hysteria2 的 Brutal 则绕开了"丢包即降速"的反馈环，按配置速率持续发送。它的有效性建立在一个前提上：链路的实际可用带宽确实高于配置值。若配置值超过链路承载能力，会加剧拥塞、触发运营商限速，反而恶化体验。这也是为什么 Hysteria2 的带宽参数必须按实测带宽的 60% 至 70% 保守设置。

一个常被忽略的事实是：在丢包率低于 3% 的链路上，三者的实测吞吐差距通常在 10% 以内，此时协议选择的影响远小于节点线路质量本身。协议差异主要在中高丢包区间被放大。

## 多终端部署与调优步骤

以下步骤以通用客户端为参照，具体菜单名称因客户端而异，逻辑一致。

1. **先测链路基线，再选协议。** 在目标网络下用 ping 与 mtr 测出到节点的 RTT 与丢包率，连续观察晚高峰时段。丢包低于 3% 优先 Reality 或 TUIC；丢包高于 8% 且 RTT 大于 150ms 时，再考虑 Hysteria2。

2. **部署 Reality 时校验回落目标。** 选择支持 TLS 1.3 与 X25519 的稳定站点作为回落目标，部署后用外部 TLS 指纹检测工具比对握手特征，确认证书链、扩展字段顺序与直接访问目标站点一致。若出现偏差，更换目标站点。

3. **配置 Hysteria2 的带宽参数。** 将上行、下行参数设为实测带宽的 60% 至 70%，首次部署后观察 24 小时内的丢包与重传情况，若出现明显拥塞迹象则继续下调。不要直接填入套餐标称带宽。

4. **调整 UDP 缓冲区与 MTU。** 在 Linux 服务端检查 `net.core.rmem_max` 与 `net.core.wmem_max`，建议不低于 16MB；QUIC 类协议对 MTU 敏感，链路存在 PPPoE 封装时将 MTU 设为 1400 至 1420 区间测试，避免分片。

5. **开启 GSO/GRO 卸载。** 在支持的网络接口上启用通用分段卸载，可显著降低高吞吐下 QUIC 的 CPU 开销，尤其在软路由与低功耗设备上效果明显。

6. **保留 TCP 回退节点。** 为每个 UDP 节点配置一个 Reality 或 TCP 系备用节点，在客户端设置自动切换或手动切换入口，应对运营商临时性 UDP 限速。

7. **分终端差异化配置。** 移动端优先考虑连接迁移与快速重连能力，QUIC 系更合适；桌面端长时间大流量场景注意 Hysteria2 的带宽占用；路由器全局代理场景下需评估 UDP 转发性能与 NAT 表容量。

## 常见失效模式与自救方案

**握手成功但无法传输数据。** 多见于 Reality 回落目标失配，或服务端时间偏差超过 TLS 容忍范围。检查系统时间同步，重新校验回落目标。

**UDP 节点间歇性可用。** 典型特征是白天正常、晚高峰失效，多为运营商 QoS。可通过更换端口段、启用端口跳跃缓解，同时准备 TCP 回退。

**Hysteria2 速度反而不如预期。** 优先检查带宽参数是否设置过高导致拥塞，其次确认 MTU 与 UDP 缓冲区配置。部分客户端默认未开启 GSO，高带宽下 CPU 成为瓶颈。

**多设备同时使用时整体变慢。** Hysteria2 的抢占性在共享网络下会挤压其他流量，降低其带宽参数或改用 TUIC 可缓解。

**连接建立慢但传输正常。** 可能为 DNS 解析或 QUIC 握手重传所致，检查客户端是否启用 0-RTT 与会话复用，并确认节点域名解析路径稳定。

协议本身没有普适的最优解。把链路质量测清楚，按丢包与 RTT 区间匹配协议，再用保守参数逐步逼近实际带宽上限，这套流程比追逐"最强协议"的标签更能带来稳定的使用体验。
