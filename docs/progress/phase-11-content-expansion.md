## 检查脚本加强

`audit-content.mjs` 新增五类检查:

1. 正文重复渲染模板已输出的区块(常见问题 / FAQ / 相关阅读 / 参考来源 / 关键结论)

## 处理的非缺陷告警

新增大量文件后 `astro build` 输出 glob-loader 的 `Duplicate id` 告警。核实过程:

```bash
find src/content -mindepth 2 -type d          # 无嵌套目录
find src/content -name "*.md" -exec basename {} \; | sort | uniq -d   # 无重名文件
```

两项均为空,确认是内容层缓存陈旧而非文件重复。清除 `.astro` 与 `node_modules/.astro` 后重建,告警消失。处理方法已写入部署文档。

附带教训:此前用 `grep -E "错误|通过|..."` 过滤 validate 输出,把这条告警滤掉了。后续查看构建输出应使用排除式过滤而不是白名单式过滤。

## 抽查产物时发现的两个聚合缺陷

自动检查全绿之后,手工核对 RSS 条目数时又查出两个问题。它们的共同点是:**链接有效、页面正常、所有检查都通过,但聚合逻辑表达的不是真正的意图。**

1. `getAllCards()` 不过滤 noindex,而首页「最新更新」直接取前 N 条。结果是示例数据页可能出现在首页,并被搜索引擎跟随。
2. RSS 按集合名硬编码排除 `reviews` 与 `comparisons`。意图是排除示例数据,但表达成了排除两个集合——一旦运营者把示例档案换成真实评测(这正是待办第一项),真实评测将永远进不了 RSS。

两个都改成按 `noindex` 过滤,并把过滤放在 `getAllCards()` 源头(`ArticleCard` 新增 `noindex` 字段)。

第二个缺陷值得单独记一笔:它只在别人完成待办事项时才会暴露,且暴露时表现为「RSS 里怎么没有新评测」,很难联想到是三个月前的一行过滤条件。**用代理条件(集合名)代替真实意图(是否可索引),是这类潜伏缺陷的典型成因。**
